18 个核心片段
① 先问业务问题

不要先背语法，先说这段代码替企业避免了什么损失或协作断点。

② 再追状态变化

找输入、输出、数据库事实、异步事件和失败分支，理解完整状态链。

③ 明确技术边界

区分 LLM 推理、确定性规则、基础设施与人工决策，不把所有节点都叫模型 Agent。

④ 最后口述表达

每张卡片读完后合上代码，用“问题—方案—权衡—结果”讲 60 秒。

Learning Objective

最终阶段目标

完成 8 天后，你要具备四种能力，而不是只记住文件名。

面试可表达
业务抽象能力

能把“商品规划效率低”拆成数据口径、证据可信度、跨角色协作、审批断点和追溯困难。

AI 方案设计能力

能解释哪些环节适合 LLM、哪些必须是确定性规则、为什么需要 RAG、Agent 编排和人工决策门。

工程落地能力

能从 React 页面一路讲到 FastAPI、Celery、LangGraph、Redis、PostgreSQL、Milvus 和模型服务。

可靠性意识

能回答幂等、重试、Checkpoint、降级、熔断、分布式锁、多租户和审计。

个人贡献边界

能讲清自己重点负责的核心链路，同时对整体系统有架构级理解，不把团队成果全部算成个人开发。

面试追问能力

能对“为什么不是单 Agent”“为什么 PostgreSQL + Milvus”“模型挂了怎么办”等问题继续追答。

Three Phases

8 天学习阶段拆解

第 1–2 天阶段一：先懂业务

不懂业务就无法判断模型输出是否有价值，也无法解释人在环、财务规则和供应约束为什么存在。

  • 企业痛点与角色
  • 业务对象和状态流转
  • 从规划到上市的价值闭环
第 3–5 天阶段二：再通全流程

沿一条请求追踪完整数据流，知道每一层输入、输出、状态和失败处理。

  • 数据治理与 RAG
  • Multi-Agent 与异步执行
  • 审批、选品、立项和前端状态
第 6–8 天阶段三：攻克重难点

把项目转换成 AI 应用开发面试中的系统设计、可靠性和权衡能力。

  • 结构化输出与证据约束
  • 人在环、恢复与一致性
  • 高并发、可观测和面试演练

项目定位

MerchPilot 不是一个“问答机器人”，而是一套以证据为输入、以 Agent 为分析工具、以人工审批为决策边界、以业务状态流转为结果的企业工作流系统。

Final Acceptance

第 8 天最终验收

30 秒项目介绍

一句话说清用户、问题、AI 能力和业务闭环。

3 分钟架构介绍

前端 → API → Celery → LangGraph → RAG → 审批 → 业务持久化。

5 个技术权衡

单 Agent / Multi-Agent、MySQL / PostgreSQL、关系库 / 向量库、同步 / 异步、模型 / 规则。

3 个故障场景

LLM 不可用、Milvus 不可用、任务重复投递时系统如何处理。

个人贡献说明

明确自己的主责链路、协作模块、验证方法和没有负责的部分。

现场演示路线

数据治理 → 规划执行 → Agent Mesh → 审批 → 正式选品 → 商品立项。
