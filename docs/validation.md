## 30. Agent node retry and execution snapshot

- Each node publishes `agent.node.started`, `agent.node.retrying`, `agent.node.failed`, `agent.node.skipped`, and `agent.node.completed` lifecycle events as applicable.
- PostgreSQL `planning_runs.execution_snapshot` stores per-node status, attempt count, maximum attempts, error, reuse flag, and timestamps so page refreshes do not lose progress.
- Retry count and base delay are configurable through `AGENT_NODE_MAX_ATTEMPTS` and `AGENT_NODE_RETRY_BASE_SECONDS`.

## 31. Failed run recovery

- `POST /api/v1/planning-projects/{project_id}/runs/{run_id}/retry` accepts only failed runs and rejects recovery while another run for the same project is active.
- Recovery reuses the original run ID, thread ID, input snapshot, partial result snapshot, and completed-node execution records.
- Completed nodes emit `agent.node.skipped`; the failed or unfinished node resumes normal execution and automatic retry behavior.
- The planning workspace exposes a `恢复失败任务` action and visually distinguishes running, retrying, failed, completed, and reused nodes.

## 32. Agent execution visibility

- The planning workspace keeps one X6 graph instance and updates node attributes in place, preventing the graph container from changing size on every WebSocket event.
- The Mesh canvas has fixed height bounds, an isolated overflow viewport, and a responsive horizontal viewing area for narrow screens.
- The execution detail panel displays all Agent nodes, persisted status, retry attempts, reused outputs, timestamps, error messages, and the latest live events.

## 33. Run event history

- `GET /api/v1/planning-projects/{project_id}/runs/{run_id}/events?limit=200` verifies project ownership before reading the Redis Stream.
- The endpoint returns chronological events with the same `event_id`, `event_type`, `occurred_at`, and `payload` shape as WebSocket messages.
- The frontend merges historical events with live WebSocket events by event ID, preventing duplicate entries during page refresh or reconnect.
