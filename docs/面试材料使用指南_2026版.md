## 二、推荐的简历版本

### 2.1 AI应用/大模型工程师

优先使用 `docs/简历项目经历_2026版.md` 中的“后端/AI岗位版”，重点保留：

1. PostgreSQL + Milvus 的 RAG 证据治理。
2. LangGraph 混合节点编排。
3. Prompt、Pydantic 和确定性规则协同。
4. Celery + Redis 异步任务与恢复。
5. 人在环审批和版本追踪。

### 2.2 Python后端工程师

使用“简历标准版”，把模型名称弱化，突出：

1. FastAPI、SQLAlchemy、PostgreSQL 事务和状态机。
2. Celery 队列拆分、幂等、锁和失败恢复。
3. 多租户、权限、审计和服务端分页。
4. Milvus 检索与业务库回查边界。
5. Docker Compose 和服务健康检查。

### 2.3 全栈/AI平台工程师

使用“全栈/平台岗位版”，补充：

1. React/Next.js、Redux Toolkit、Axios。
2. AntV X6 Agent Mesh 和 WebSocket 运行时间线。
3. FastAPI 与前端类型契约。
4. Docker 多服务联调。
5. FastMCP 受控能力开放。

## 三、项目介绍的时间控制

### 30秒

只回答四件事：

1. 项目服务什么业务。
2. 解决什么痛点。
3. 核心技术方案是什么。
4. 你负责什么。

不要在30秒版本里主动展开Agent数量、所有数据库和全部页面。

### 3分钟

按以下顺序：

1. 业务背景和目标，约30秒。
2. 数据治理与RAG，约40秒。
3. LangGraph混合Agent工作流，约50秒。
4. Celery、Redis和恢复机制，约35秒。
5. 人工审批与商品闭环，约30秒。
6. 个人职责和边界，约25秒。

### 10分钟深挖

只选择两个核心难点深入，不要平均介绍所有模块。推荐组合：

- 难点一：Milvus召回后为什么必须回PostgreSQL治理。
- 难点二：Celery长任务如何做到节点级重试和状态恢复。
- 备选难点：为什么财务、供应和评分不交给LLM直接计算。
- 备选难点：人工审批等待数小时后如何恢复工作流。

## 四、专业面试表达结构

每个技术问题都使用“背景—选择—实现—异常—结果”五段式：

1. **背景**：业务上遇到了什么约束。
2. **选择**：为什么选择该技术，而不是罗列技术名称。
3. **实现**：数据流、状态流和关键代码在哪里。
4. **异常**：服务不可用、重复请求、越权或刷新时如何处理。
5. **结果**：实现了什么可验证能力；没有生产数据时不要虚构比例。

示例：

> 商品规划一次运行包含检索、模型和报告生成，同步HTTP容易超时，所以我们使用Celery拆成长任务。API先持久化运行记录，再投递任务；Worker按规划、索引和报告分队列执行，节点状态同时写入PostgreSQL运行快照和Redis事件。节点失败时只对当前节点指数退避，重试耗尽后可以复用已完成输出恢复。这样页面刷新和Worker重启不会让业务运行完全丢失。

## 五、面试官最可能追问的五个点

### 1. “为什么需要这么多Agent？”

回答重点不是数量，而是职责和失败边界。明确说明只有 5 个 LLM Agent，7 个是确定性工具，1 个是人工门禁；导入链路另有 1 个多模态 LLM Agent。

### 2. “为什么关系库和向量库都要用？”

回答事务事实与语义索引的职责分离，以及Milvus命中后回PostgreSQL校验。

### 3. “怎么证明不是一个Demo？”

展示真实业务实体、数据库迁移、Celery任务、审批状态、版本修订、审计记录、正式选品和试销流程；同时诚实说明当前是本地Docker可验收系统，不是企业生产上线系统。

### 4. “模型输出错了怎么办？”

回答证据约束、Pydantic契约、确定性计算、方案审查、降级状态和人工审批。

### 5. “你本人到底写了什么？”

只围绕RAG检索治理、LangGraph编排、Prompt/结构化输出、Celery/Redis恢复和相关测试展开；整体页面和商品闭环说“参与、协同、能解释”，不要全部归为个人独立开发。

## 六、材料一致性检查表

面试前确认以下说法保持一致：

- [ ] 数据库说 PostgreSQL，不再说当前项目使用 MySQL。
- [ ] SQLAlchemy 是 ORM/数据库访问层，不与 PostgreSQL 冲突。
- [ ] 规划 Mesh 是13个节点，不是13个LLM Agent。
- [ ] Agent Catalog 总计14个定义，其中1个属于导入流水线。
- [ ] Redis保存过程状态，PostgreSQL保存最终业务事实。
- [ ] Milvus保存证据向量，不保存审批和业务状态。
- [ ] 人工审批在系统内完成；外部OA只是预留接口。
- [ ] 本地使用Docker Compose全量运行。
- [ ] 企业SSO、阿里云OSS和生产监控没有宣称正式接入。
- [ ] 不提供未经压测验证的QPS、准确率和生产SLA。
